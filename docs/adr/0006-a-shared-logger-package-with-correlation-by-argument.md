# A shared logger package, with correlation carried by argument, not by injection

Every app builds its logger from one factory in `packages/logger` (`createLogger({ name, bindings? })`), which owns the log format, the default verbosity per environment, and a redaction safety net, so none of that drifts between `apps/api`, `apps/worker`, `apps/waitlist` and `apps/web` the way it had started to: before this, `apps/api` got Pino only as Fastify's untouched default, `apps/worker`/`apps/waitlist` had about fifteen scattered `console.*` calls, and `apps/web` had none. `packages/logger` is shared infrastructure in exactly `packages/db`'s sense, not a feature — see [Architecture](../architecture.md) and [Logging](../logging.md) for the shape.

A request's or a job's id is bound to its logger with Pino's `.child()`, but that child logger is handed to business logic as a plain argument (`request.log` in a controller call, a job-scoped `.child({ itemId })` passed where a processor calls a use case) rather than resolved through `apps/api`'s or `apps/worker`'s dependency-injection container. A container binding is a singleton for the process's life (ADR 0004); a request or a job's correlation id is not — it's a new value on every call. Nothing today actually needs this (no use case logs internally yet in either app), so the convention is written down at the call site closest to where it will eventually be used — a comment on `ItemsController` in `apps/api`, and on `WORKER_TOKENS.Logger`'s binding in `apps/worker/src/di/container.ts`, describing the short-lived Inversify child-container mechanism for the worker's case — rather than implemented as unused plumbing ahead of a real need.

`apps/waitlist` (ADR 0005, no DI container) and `apps/web` (nothing server-side logs yet) each get a single plain logger singleton instead: correlation is deliberately not added to either, since a single low-traffic endpoint and an app with no log calls yet don't carry the cost of threading a per-request id to justify it.

## Considered Options

- **Each app configures Pino independently**: no new shared package, but the format, redaction, and verbosity rules would need to be kept in step by hand across four apps, which is exactly how the project arrived at inconsistent logging in the first place.
- **Inject a request/job-scoped logger through the DI container** (a request-scoped child container per request in `apps/api`, rebuilding part of the graph per job in `apps/worker`): keeps every dependency flowing through `@inject`, matching ADR 0004 to the letter, but a container binding that changes on every call, rather than once per process, doesn't fit the "container is the only place that constructs application classes, binding singletons and transients" shape ADR 0004 already settled on — it would need a second, parallel scoping mechanism alongside it.
- **One redaction mechanism, chosen as the deep recursive walk, not Pino's own path-based `redact.paths` alongside it**: the first version of this work configured both; `redact.paths` only duplicated a guarantee the walk's `SENSITIVE_KEYS` list already covered generally ("masked regardless of where it appears" needs exactly one general mechanism, not two to keep in sync). Removed in review.
- **Recurse into every object redaction encounters, including `Error`/`Date`/Fastify's `Request`/`Reply`**: rejected after it was caught doing real damage — `Object.entries`-based recursion silently flattens any object that exposes its data through prototype getters (which is exactly what `Request.method`/`url`/`statusCode` are) into `{}`, which would have broken Fastify's own request-completion logging the moment real redaction ran. The walk is scoped to genuine plain objects instead.

## Consequences

- A future use case that wants to log takes its logger as a parameter passed by its caller, not as a constructor dependency — reviewers should expect this asymmetry with every other port in `apps/api`/`apps/worker`, and know why: it's the correlation id changing per call that rules out a singleton binding, not an inconsistency in how the rest of DI works there.
- If request- or job-scoped logging is ever actually wired into a use case, the worker's mechanism (an Inversify child container created per job, rebinding just the logger token) is already designed and commented at its binding site — implement it there rather than inventing a different approach.
- `describeError` (an error's name and code, never its message) moved from `apps/waitlist` into `packages/logger`, so `apps/worker` could adopt the same no-PII discipline for its own error logging without duplicating the helper. Any future app joining this project should import it from there, not reinvent it.
- Redaction is a safety net, not the primary defense. A call site that passes a raw `Error` into a log call (instead of `describeError(error)`'s safe string) is still a bug, even though the field-name-based redact walk would mask a field literally named `password` or `token` if one somehow got there — the walk can't know a field it's never heard of is sensitive.

# Queue & Background Jobs

Async processing is handled with [BullMQ](https://docs.bullmq.io) backed by Redis. The reasoning: link fetching, metadata extraction, and AI tagging are all slow/unreliable enough that they can't block the save request (see product plan, section 10) — a user pastes a link, the item appears immediately as `processing`, and a worker fills in the rest.

## Current state: the API produces, the worker detects the Item type, title and description, keeps Thumbnails for Images and pages, and AI-tags Ready Items

`POST /items` (see [API](./api.md#post-items)) stores a Processing Item, then enqueues one **Process Item** job on the **Item processing queue**. The processing worker consumes it: **usually** it fetches the Source URL itself (guarded) — but when the job carries already-rendered page content, captured by the browser extension, it skips that fetch entirely and works from the given content instead (see [Captured content: the browser extension path](#captured-content-the-browser-extension-path)). Either way, from that point on the same code decides: works out the Item type from the URL's shape, then the response, then oEmbed and the page's own declarations, reads the page's title and description, keeps a Thumbnail from an Image Item's image or the picture a page advertises (see [Thumbnails](#thumbnails)), and marks the Item Ready with them; once the job fails with no attempt left (its last retry, or a stall), it marks the Item Failed. Once an Item is Ready, the processing worker queues a second job for it on a queue of its own, the **Item tagging queue**: **Tag Item**, which a separate tagging worker works through to put AI Tags on it (see [AI tagging](#ai-tagging)). The two queues are consumed by two worker processes, so neither can hold up or take down the other (see [Items ADR 0005](./contexts/items/adr/0005-processing-and-ai-tagging-have-their-own-queues-and-worker-processes.md)); see [Running the workers](#running-the-workers).

- **Shared names and payload.** `@resonory/shared/schemas/queue` exports `ITEM_PROCESSING_QUEUE` (`"item-processing"`), `PROCESS_ITEM_JOB` (`"process-item"`) and `ProcessItemJobSchema` / `ProcessItemJob`: `{ itemId, userId, html, captions }`, `itemId`/`userId` both UUIDs, `html` optional (issue #143/#145 — see [Captured content](#captured-content-the-browser-extension-path)), `captions` optional (a YouTube video's plain caption text, issue #164 — see [Text](#text)). Only ids (and, when present, the captured content itself) travel through Redis; the worker loads the Item itself, scoped to its User. It also exports `ITEM_TAGGING_QUEUE` (`"item-tagging"`), `TAG_ITEM_JOB` (`"tag-item"`) and `TagItemJobSchema` / `TagItemJob`: `{ itemId, userId }`, ids only. The Item tagging queue carries only Tag Item jobs, so its worker has no job-name routing. The Item processing queue carries Process Item jobs from the API and one repeating job of the worker's own, the stuck-Item sweep (`sweep-stuck-items`, see [Stuck Items](#stuck-items)), so its worker routes on the job name. Both apps use these constants and the schemas, never typed-out strings. The old `items` queue no longer exists (see [Before deploying](#before-deploying-drain-the-old-items-queue)).
- **Producer (`apps/api`).** `SaveItemUseCase` depends only on the `IQueueProvider` port (`domain/providers/IQueueProvider.ts`, `enqueueProcessItem({ itemId, userId })`, typed by the port's own `ProcessItemRequest`, since the domain imports nothing outside itself). `BullMqQueueProvider` (`infrastructure/queue/`) implements it: it maps the request to the shared payload and parses it with `ProcessItemJobSchema`, so a payload the worker would refuse never reaches Redis, then adds the job with the defaults below. The BullMQ `Queue` itself is built once in `infrastructure/queue/itemProcessingQueue.ts` on the shared Redis connection and bound as `TOKENS.ItemProcessingQueue`; only the container imports it. The API only ever produces Process Item jobs onto the Item processing queue; it never queues a Tag Item job. The lint guard keeps `bullmq` out of domain and application code.
- **Job defaults (Item processing queue).** 3 attempts with exponential backoff from 5 s (so retries 5 s and 10 s later), `removeOnComplete: 1000` and `removeOnFail: 5000` so Redis doesn't keep job history forever. A kept job doesn't keep its payload's bulk: once a job is finished (done, or failed with no attempt left), the worker rewrites its data without what its handler's `slimmed` step drops (`slimFinishedJob` in `interface/itemProcessingWorker.ts`), which is the captured `html` and `captions`, leaving its ids. A retried job keeps them for its next attempt. A Redis error there is logged as a warning and never fails or retries the job.
- **If enqueueing fails** (Redis down), `POST /items` answers `500 internal`. The Item is already stored and stays Processing until the stuck-Item sweep ends it as Failed (see [Stuck Items](#stuck-items)); there is no retry endpoint yet.
- **Consumer: the processing worker (`apps/worker`).** `src/itemProcessing.ts` is its entry point: it builds the processing container (`di/processingContainer.ts`), pings Redis and starts `createItemProcessingWorker` (`interface/itemProcessingWorker.ts`): a BullMQ `Worker` on `ITEM_PROCESSING_QUEUE` over the shared Redis connection, with the concurrency, optional limiter and lock duration the `ITEM_PROCESSING_*` settings give it (concurrency 1, no limiter and BullMQ's lock duration when unset; see [Worker limits](#worker-limits)). The queue carries Process Item jobs and one repeating job, the stuck-Item sweep (see [Stuck Items](#stuck-items)); the worker routes on the job name, and a job with any other name throws `UnrecoverableError`, so it fails without a retry. The Process Item processor (`interface/processors/processItem.processor.ts`) parses `job.data` with `ProcessItemJobSchema`; an invalid payload throws `UnrecoverableError`, so it fails without a retry. Otherwise it runs `ProcessItemUseCase` from the worker's container and logs the outcome. An Item that is already Ready (a job re-run after a stall, say) is left alone: the use case answers `already_ready` before fetching, writing or queueing a Tag Item job, and the processor logs it with `event: "item_already_ready"`. A Processing or Failed Item still runs, so a Failed Item that a late job finishes becomes Ready. The job has no `jobId`: every save makes a new Item and nothing re-queues a Failed Item, so an Item-id `jobId` would dedupe nothing (and, kept with the finished jobs, would block a future retry endpoint's re-queue). The container holds the page fetcher, parsers, Thumbnail pipeline and a producer onto the Item tagging queue, and no AI client, so a missing or wrong AI key can't stop it from booting. On SIGINT/SIGTERM the worker finishes its current job (`worker.close()`), closes the queue it produces onto (see [AI tagging](#ai-tagging)) and the Item processing queue it registers the sweep on, then closes Redis.
- **Processing.** `ProcessItemUseCase` loads the Item scoped to its User (a deleted Item is nothing to do: the job completes), applies the URL rules (`domain/rules/itemTypeFromUrl.ts`) and, when the job carries no captured content, fetches the Source URL once through the `IUrlFetcher` port (`domain/providers/IUrlFetcher.ts`), **every such Item, typed or not**, for its title and description (a job that does carry captured content skips this fetch — see [Captured content](#captured-content-the-browser-extension-path)). The fetch reports the final URL after redirects, and the Item type is the first signal that answers, in the order in [Detection order](#detection-order) (so a short link such as `bit.ly`, `t.co` or `lnkd.in` to YouTube becomes a Video). The Item becomes Ready with its type, title, description and Thumbnail key, in one update. The Source URL is never changed: it stays as pasted.
- **When the fetch fails.** A refused, failed or timed-out fetch (or a 5xx/429 answer) doesn't need to fail an Item a URL rule already typed: it becomes Ready with that type, titled by its known oEmbed provider when its Source URL has one (an X post behind a login wall still gets its title; see [oEmbed](#oembed)), else with no title or description. An Item with no type yet rethrows, so BullMQ retries with the defaults above and, out of attempts, it ends Failed as a Link. Any other error (Postgres down) propagates either way.
- **Failure.** `createItemProcessingWorker` listens for the Worker's `failed` event with `onItemProcessingJobFailed` (`interface/itemProcessingWorker.ts`). Every failed attempt is logged with its job, attempt number and reason; the reason is not stored. An attempt BullMQ will retry leaves the Item Processing. Once no attempt is left, BullMQ moves the job to the failed set and sets `job.finishedOn`; that is the handler's signal, whatever the attempt count says. It covers the last retry, an unrecoverable error, and a job that stalled more than the Worker's `maxStalledCount` allows (default 1; BullMQ fails it with `UnrecoverableError: job stalled more than allowable limit` when it's next picked up, attempts left or not). Then `processItemFailed` (`interface/processors/processItemFailed.processor.ts`) runs `FailItemUseCase`: the Item becomes Failed, and an Item with no Item type yet becomes a Link, so it still displays like any other Item. An invalid payload names no Item, so it changes none. If the final-failure step throws, the handler logs "couldn't mark the Item Failed" and the Item stays Processing until the sweep ends it (see [Stuck Items](#stuck-items)). A failed sweep job changes no Item: its data names none, so it is only logged. There is no separate dead letter queue: a job out of attempts stays in BullMQ's failed set (`removeOnFail: 5000`), and the Item's Failed status is what a User sees ([Items ADR 0007](./contexts/items/adr/0007-exhausted-jobs-stay-in-the-failed-set-with-no-dead-letter-queue.md)). A failed Tag Item job never reaches this handler: it is on the other queue and never changes an Item (see [AI tagging](#ai-tagging)).

### URL rules

`itemTypeFromUrl(url)` (`domain/rules/itemTypeFromUrl.ts`) is pure and works on any URL, pasted or reached by redirect: it returns an Item type, or null when no rule matches (the response and the page decide). It tries the **known-site table** first, then the **file extension** ending the path. Only the URL's path is matched, never its query or fragment.

**Known sites** (`domain/rules/knownSites.ts`, `KNOWN_SITES`) is plain data: each row is hosts, an optional path pattern, an Item type and, for a site with one, its oEmbed endpoint (see [oEmbed](#oembed)) and its known-site Text extractor (see [Text](#text)), so adding a site is one row. Hosts are compared lower-case without a leading `www.` or `m.`; `*.example.com` matches any subdomain and `*` any host that no other row names. Rows run in order and the first match wins (`knownSiteFor`), so a GitHub issue (Post) sits above a GitHub repository (Code). The any-host Mastodon row sits last and never applies to a named host, so `replit.com/@user/123` stays Code and `youtube.com/@channel/123` matches nothing. Profiles, homepages and listings on these hosts match no row and are typed by the page like any other.

| Item type | Known sites                                                                                                                                                                                                                                                             |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Video     | YouTube (`/watch`, `/shorts/`, `/live/`, `youtu.be`), Vimeo, TikTok videos and `vm.`/`vt.` short links, Twitch videos and clips, Dailymotion (`dai.ly`), Loom, Instagram reels, Facebook videos (`fb.watch`)                                                            |
| Audio     | Spotify tracks, albums, playlists, episodes and shows; SoundCloud tracks and sets; Apple Podcasts; Apple Music albums, playlists and songs; Bandcamp tracks and albums                                                                                                  |

### Detection order

`itemTypeOf` in `ProcessItemUseCase.ts` is the one place the order is written down; the first signal that answers wins:

1. the URL rules on the Source URL as pasted, then on the final URL ([URL rules](#url-rules));
2. a file's (a 2xx non-HTML response's) Content-Type, then its magic bytes ([Response rules](#response-rules));
3. oEmbed ([oEmbed](#oembed)), then the page's JSON-LD, then its Open Graph tags, then its Twitter Card ([Page rules](#page-rules));
4. Link (anything else).

**A 4xx answer** (other than 429) on an Item no URL rule typed is not a failure: the fetch resolves as an unsuccessful answer that says nothing about the page, so the Item becomes Ready as a **Link, with no retry** (a missing or forbidden page won't answer differently a few seconds later). Only a 5xx, a 429, a timeout or a refusal fails the fetch and so retries an untyped Item (see Processing above).

Why this order, and why Item types are content forms rather than sites: [Items ADR 0001](./contexts/items/adr/0001-item-types-are-content-forms-detected-in-a-fixed-order.md).

### Response rules

`SafeUrlFetcher` (`infrastructure/http/`) implements `IUrlFetcher`: one GET, guarded against server-side request forgery (see [Security](./security.md#the-workers-url-fetch)). It returns a `FetchedPage` tagged by `kind`, each with the final URL: `html` (the Content-Type and the parsed head), `file` (the Content-Type and the first 16 bytes) or `unsuccessful` (the status of a 4xx answer, nothing read). A 2xx body sent **without a Content-Type** is HTML when its first bytes start like it (`looksLikeHtml`: `<!doctype html`, `<html` or `<head`, any case, after an optional BOM and whitespace; up to 512 bytes are read to decide), so its head is read and its page rules and oEmbed discovery run; otherwise it is a file. `itemTypeFromResponse` (`domain/rules/itemTypeFromResponse.ts`, pure) types a file, first match wins, else null:

| Response                                                                                           | Item type |
| -------------------------------------------------------------------------------------------------- | --------- |
| a Content-Type `itemTypeFromContentType` knows (below)                                             | its type  |
| no Content-Type, or `application/octet-stream`: magic bytes `itemTypeFromMagicBytes` knows (below) | its type  |
| anything else                                                                                      | none      |

`itemTypeFromContentType` (`domain/rules/itemTypeFromContentType.ts`): `application/pdf` (an arXiv paper without `.pdf`) → PDF; `image/*` → Image; `audio/*`, `application/ogg` → Audio; `video/*` → Video; archives (zip, gzip, tar, 7z, rar …), office documents (Word, Excel, PowerPoint, OpenXML, OpenDocument, RTF), EPUB, disk images and installers (dmg, iso, exe/msi, deb, rpm, apk) → File.

`itemTypeFromMagicBytes` (`domain/rules/itemTypeFromMagicBytes.ts`), for a server that is vague about what it sends: `%PDF-` → PDF; PNG, JPEG, GIF, WebP, TIFF, and ISO media files branded `avif`/`heic` → Image; ID3 or an MPEG frame (MP3), OGG, WAV, FLAC, and ISO media files branded `M4A` → Audio; other ISO media files (MP4, MOV), WebM/MKV, AVI → Video; ZIP (and so docx/xlsx/jar), gzip, 7z, RAR → File.

A 5xx or 429 answer fails the fetch instead (see Processing above). Of an HTML body at most ~1 MB is read, only up to `</head>`; of any other body only the first 16 bytes.

### Captured content: the browser extension path

For the full before/after comparison (old server-fetch path vs. this one, side by side) see [Content capture](./content-capture.md). The motivating problem (issue #137, [ADR 0007](./adr/0007-v1-capture-is-a-browser-extension-not-paste-a-link.md)): a page behind Cloudflare or a login wall answers `SafeUrlFetcher`'s guarded, cookieless, server-side request with a challenge or a blank page — the Item still gets typed if a URL rule can do it from the link alone, but never a real title, description or Thumbnail. No server-side fix closes this: the block is on the fetch itself, at the TLS/fingerprint level, not fixable by request tweaking. The browser extension (issue #143/#145/#146) solves it by never asking the server to fetch that page at all.

On a toolbar click, the extension's background script injects a capture function into the **active tab only** (`chrome.scripting.executeScript`, granted by the `activeTab` permission for that one click — no broad host permissions, no always-on content script), which reads clones of `document.head` (stripped of styles, `noscript`, `template` and every script but JSON-LD) and `document.body` (stripped of scripts, styles, `noscript`, `svg`, `iframe` and `template`), both without inline `data:` URIs (the live page is never modified; a page still over the 5 Mi cap is sent as its head alone), straight off the page's own, already-rendered DOM — past whatever challenge or login the user's real browser session already cleared — and sends it alongside the URL to `POST /items` as the optional `html` field ([API](./api.md#post-items)), authenticated via an API key ([Authentication](./security.md#authentication)) rather than a Session cookie. `SaveItemUseCase` carries it unchanged into the enqueued job.

In `ProcessItemUseCase`, a job whose `html` is present skips `IUrlFetcher.fetchPage` entirely and instead builds the identical `FetchedPage` shape a successful fetch would have produced (`pageFromContent`): `kind: "html"`, the Source URL as its final URL (there was no fetch, so no redirect to learn), and a head parsed from the given HTML by the same `IPageHeadParser` a fetched page's head goes through. Every step after that — [Detection order](#detection-order), [oEmbed](#oembed), [Page rules](#page-rules), title/description precedence, [Thumbnail candidates](#thumbnails), the URL preview cache — runs completely unchanged: there is no second extraction pipeline to maintain, only this one branch deciding where the `FetchedPage` came from.

**The one structural difference**: a captured page's `finalUrl` is always exactly its `sourceUrl`, since there's no redirect step to observe. A server fetch can land somewhere else after redirects, and that final URL is what the cache keys on — so a captured Item's cache key is always the URL the user actually looked at, never a resolved redirect target. Only a captured page gets Text — see [Text](#text).

### oEmbed

oEmbed gives a clean type and title in one small JSON call, even for pages behind a login wall (an X post, a Reddit thread). For an HTML page, or a page that answered 4xx, Processing asks **at most one** oEmbed endpoint, through the `IOEmbedProvider` port (`domain/providers/IOEmbedProvider.ts`). `oEmbedRequestFor` (`domain/rules/oEmbed.ts`, pure) picks it:

1. a **known provider's endpoint**, chosen from the final URL: the matching known-site row's `oEmbed` endpoint (`knownOEmbedRequestFor`; the provider's hosts and paths are that row's, never a copy): YouTube (one endpoint for `youtube.com` and `youtu.be`), Vimeo, X (`publish.twitter.com`), Spotify, SoundCloud, Reddit and TikTok, asked with `?url=<final URL>&format=json`;
2. otherwise the page's first **discovery link** of JSON format (`<link rel="alternate" type="application/json+oembed">`), used as written. It's an untrusted URL like any Source URL, so the guard checks it the same way.

When the **page fetch itself fails** (a timeout, a 5xx or 429, a refusal) for an Item a URL rule typed, the known provider for the Source URL is still asked (still once): an X post that never answers the worker still gets its title, and its `thumbnail_url` is still tried as the Thumbnail. The URL rule keeps the type; oEmbed only adds the title and the Thumbnail.

`GuardedOEmbedProvider` (`infrastructure/http/`) implements the port over the `IJsonFetcher` port (`WORKER_TOKENS.JsonFetcher`, the same `SafeUrlFetcher` instance as the page fetch, through its `fetchJson`): the same guard, redirect checks and 10-second timeout as the page fetch, JSON only, at most 64 KB (see [Security](./security.md#the-workers-url-fetch)). It reads only the answer's `type`, `title` (entities decoded) and `thumbnail_url` (kept only as an absolute http(s) URL, for the Thumbnail); an answer without a title (X's) is titled by the text of the post its embed HTML quotes. `itemTypeFromOEmbed` types the answer:

| oEmbed `type` | Item type                                                                                                                          |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `video`       | Video                                                                                                                              |
| `photo`       | Image                                                                                                                              |
| `rich`        | the known provider's: Post (X, Reddit), Audio (Spotify, SoundCloud), Video (YouTube, Vimeo, TikTok); none from an unknown provider |
| `link`, other | none                                                                                                                               |

A discovery link pointing at a known provider's endpoint counts as that provider. A refused, failed, timed-out, non-JSON, oversized or unreadable answer never fails Processing: the page's other signals decide, as if there were no oEmbed. A response that isn't HTML (a file) asks nothing, and so does a failed page fetch for an Item without a known provider.

### Page rules

The fetcher parses an HTML head once, in infrastructure (`parsePageHead.ts`, htmlparser2), into a `PageHead` (`domain/entities/PageHead.ts`): its meta tags (keyed by `property`, else `name`, lower-case), its first `<title>`, each JSON-LD block that parses as JSON (a `<script>` whose type `isJsonLdType` from `@resonory/shared/html` accepts: `application/ld+json` in any case, with or without parameters; the extension's capture keeps head scripts by the same rule), and its oEmbed discovery links (absolute). Entities are decoded there. The domain rules read only these tags:

| Rule                                       | Declares                                                                                  | Item type |
| ------------------------------------------ | ----------------------------------------------------------------------------------------- | --------- |
| `itemTypeFromJsonLd` (`@type`)             | Article, NewsArticle, BlogPosting                                                         | Article   |
|                                            | VideoObject                                                                               | Video     |
|                                            | AudioObject, PodcastEpisode, MusicRecording                                               | Audio     |
|                                            | SoftwareSourceCode                                                                        | Code      |
|                                            | SocialMediaPosting, DiscussionForumPosting                                                | Post      |
|                                            | ImageObject, only when no other type above is declared (WebPage and the like don't count) | Image     |
| `itemTypeFromOpenGraph`                    | `og:type` article                                                                         | Article   |
|                                            | `og:type` `video.*`, or (when `og:type` says nothing above) an `og:video` tag             | Video     |
|                                            | `og:type` `music.*`                                                                       | Audio     |
| `itemTypeFromTwitterCard` (`twitter:card`) | `player`                                                                                  | Video     |
|                                            | `photo`                                                                                   | Image     |

JSON-LD nodes are read at the top level, in arrays and in `@graph`, in document order (the first recognised type wins), never inside properties; `schema:Article` and `https://schema.org/Article` count as `Article`.

**Title and description** (`domain/rules/pageMetadata.ts`), each field on its own, from the first source with a non-blank value: the oEmbed title (oEmbed has no description), then Open Graph (`og:title`, `og:description`), then Twitter Card (`twitter:title`, `twitter:description`), then the page (`<title>`, `<meta name="description">`). Whitespace is collapsed; the title is capped at 300 characters and the description at 1000 (cut with an ellipsis). A response that isn't HTML gives neither; a 4xx answer or a failed fetch gives only what a known oEmbed provider says. They are written to the Item's `title` and `description` columns as it becomes Ready.

What else it builds on:

- **The Redis connection.** `@resonory/db/redis` exports `redisConnection`, built once with `maxRetriesPerRequest: null` because BullMQ's blocking commands need it. The API's Item processing queue and each worker's queues use it directly; the rate-limit store uses its own fail-fast duplicate of it (see [Security](./security.md#rate-limiting)).
- **The Items domain and output.** The `Item` and `Tag` entities, the Tag name rule and the Item card output are in `apps/api` (see [Clean Architecture](./clean-architecture.md#the-four-layers)), and the `items`, `tags` and `item_tags` tables are in `packages/db` (see [Database](./database.md)).

### Thumbnails

Implemented for **Image Items**, **HTML pages** and **oEmbed answers**. The candidates, best first, come from one pure rule, `domain/rules/thumbnailCandidates.ts`, the one place the order is written down: for an Image Item whose fetch ended at the image file, only that final URL; otherwise the oEmbed answer's `thumbnail_url` (a provider's deliberate answer beats page markup, as for the title), then an HTML page's `og:image`, then its `twitter:image` (from the oEmbed answer and the head Processing already has, so no extra request). Each value is made absolute against the final URL after redirects, blank values and ones that aren't http(s) (`data:`, `javascript:` …) are dropped, and an image offered twice is tried once. Other files have no candidate; an unsuccessful answer, or a failed page fetch for an Item a URL rule typed, has only its oEmbed `thumbnail_url`, so a post behind a login wall can still get one. Processing tries the candidates in order and keeps the first that works ([ADR 0002](./contexts/items/adr/0002-thumbnails-are-resized-by-the-worker-and-kept-in-private-supabase-storage.md)):

1. **Download** each candidate in turn through the `IImageFetcher` port, bound to the same `SafeUrlFetcher` as the page (`fetchImage`): guarded, at most 5 MB, only JPEG, PNG, WebP, GIF or AVIF whose Content-Type and magic bytes agree (see [Security](./security.md#the-workers-url-fetch)). An Image Item's image is downloaded again in full; the page fetch read only its first 16 bytes.
2. **Resize** through `IThumbnailResizer`, `SharpThumbnailResizer` (sharp): turned by its EXIF orientation, at most 800px wide (never enlarged), WebP, all metadata stripped, the first frame of an animated image; an image declaring more than 40 megapixels, an undecodable one, or one sharp decodes as another format (SVG, TIFF, HEIC …) is refused.
3. **Store** through `IThumbnailStore`, `SupabaseThumbnailStore`: an upsert to `{userId}/{itemId}.webp` (`domain/rules/thumbnailKey.ts`) in the private `thumbnails` bucket, as `image/webp`, so a retry or a reprocess overwrites the same object.

The key goes to `items.thumbnail_key` in the same update as the type, title and description. Any failure (a refused or failed download, an image that can't be decoded or resized, a failed upload) moves on to the next candidate. None of these fails Processing or retries the job: with no candidate left, the Item goes Ready with no Thumbnail. Without `SUPABASE_URL` or `SUPABASE_SERVICE_ROLE_KEY` the container binds no Thumbnail store (`ProcessItemUseCase` takes it as optional), and Processing downloads no image at all. The bucket is created once by hand (see [Getting Started](./getting-started.md#thumbnail-storage)).

### Text

An Item's **Text** is a YouTube video's captions when the job carries them, otherwise its page's main content: an Article's body, with no navigation, footer or sidebars, or an X post's own words, with no replies or timeline. Only a job with captured content gets it; the server-fetch path, failed or not, writes none, even for a job that carries captions without `html`. `ProcessItemUseCase` computes it once per job, from the job's captions and captured HTML alone (not the Item type, not the oEmbed answer), **before** the URL preview cache is looked up, so a cache hit and a miss both write it, in the same update that marks the Item Ready (`items.extracted_text`). It's never cached: Text is the User's own, from what their browser showed them ([Items ADR 0003](./contexts/items/adr/0003-an-items-text-is-never-shared-across-users.md)), so the Ready shape is the `CachedPreview` plus `text`, and the cache only ever gets the preview.

1. **Captions first.** The extension reads a YouTube video's captions in the User's tab ([Browser extension](./extension.md#youtube-captions)) and sends them as `captions`, carried unchanged through `POST /items` and the job. When they aren't blank they are the Text, and the page is never extracted.
2. **Otherwise, extract** the page through the `ITextExtractor` port, `ReadabilityTextExtractor` (`infrastructure/http/`), which parses the captured HTML with linkedom and tries, in order:
   1. a **known-site extractor**, for a page whose known-site row names one in its `text` field: `knownTextSourceFor` (`domain/rules/knownTextSource.ts`, pure) picks it from the page URL, with the id of the post the URL names (the row's `postId` pattern), so the site's hosts, paths and post-id pattern are that row's, never a copy; `ReadabilityTextExtractor` maps each extractor's name to its reader in one `Record` (`KNOWN_SITE_TEXT`), so adding a known site's extractor is its row, its name and one entry there (tsc asks for the entry). Only X has one (`xPost`, for `x.com` and `twitter.com` status links): `xPostText` reads the text node (`[data-testid="tweetText"]`) of the post cell (`article[data-testid="tweet"]`) whose permalink, the link around its `<time>`, is the URL's status id. The replies below it, a post it replies to above it, a post it quotes, and the sidebar's "Who to follow" and trends are never read. Line breaks are kept as X renders them, and an emoji image is its `alt`. It reads the User's own capture, not the oEmbed answer, so a preview-cache hit (which skips oEmbed) still gets it. A page without that cell, or a post without words (a photo alone), falls through to the next step;
   2. **main-content extraction**: Mozilla Readability, gated by `isProbablyReaderable`, so a homepage or a product page with no main content has none. Block elements become blank lines and a `<br>` a line break, so paragraphs don't run together. Every other network's Post (Reddit, LinkedIn, Bluesky …) gets its Text this way.
3. **Normalise** with the pure rule `itemText` (`domain/rules/itemText.ts`), which also decides that precedence (its page text is asked for lazily, only when the captions don't answer): each line's whitespace collapsed to single spaces and trimmed, at most one blank line in a row, capped at `MAX_TEXT_LENGTH` (100,000 characters, the search vector's cutoff); blank text is none.

An extractor that throws counts as none, but isn't silent: `ProcessItemUseCase` hands the error back on its Ready result (`textError`, the use case itself never logs), and `processItem.processor.ts` logs a warning with `describeError` (its name and code, never its message) before the Ready line. Extraction runs synchronously (linkedom and Readability over up to 5 Mi characters, about 3.5 s for a synthetic 5 Mi page), holding the worker up meanwhile, so the use case also hands back how long the extractor ran (`textMs`) and the Ready line logs it whenever it ran. Missing Text never fails Processing or retries the job: the Item goes Ready with its type, title, description and Thumbnail, and no Text.

### AI tagging

Once an Item is Ready, the worker puts 0–3 Tags on it with Tag source `ai` (issue #178; what it does and why is in [Tags → AI tagging](./tags.md#ai-tagging), what's sent to the model in [Items ADR 0004](./contexts/items/adr/0004-ai-tagging-sends-an-item-excerpt-to-a-third-party-model.md)). It's a job of its own, on its own queue and in its own worker process, so a slow, failing, crashing or unconfigured model never delays Ready and never makes an Item Failed.

- **Producer (the processing worker).** `ProcessItemUseCase` queues a Tag Item job right after `markReady`, on every path that reaches Ready (fetched, captured, a cache hit, or a typed Item whose fetch failed), through its `IQueueProvider` port (`domain/providers/IQueueProvider.ts`, `enqueueTagItem({ itemId, userId })`). The worker's `BullMqQueueProvider` (`infrastructure/queue/`) parses the payload with `TagItemJobSchema` and adds it to the Item tagging queue; that BullMQ `Queue` is built once in `infrastructure/queue/itemTaggingQueue.ts` on the shared Redis connection and bound as `WORKER_TOKENS.ItemTaggingQueue`, typed by the worker's `ItemTaggingQueue` (`add` for the provider, `close` for shutdown). A Failed Item retried to Ready is queued again. If queueing fails, the Item stays Ready without AI Tags: the use case hands the error back (`tagQueueError`) and the Process Item processor logs a warning with the stable key `event: "tag_item_enqueue_failed"` (search for it to count how often an Item is left untagged this way), so Processing is never retried over it.
- **Job defaults (Item tagging queue).** 3 attempts with exponential backoff from 30 s (retries 30 s and 60 s later, long enough for a free tier's per-minute rate limit to reset), and the same `removeOnComplete: 1000` / `removeOnFail: 5000`. Its payload is only ids, so there's nothing to slim once it's finished.
- **Concurrency and rate limit.** The tagging worker runs one job at a time, with no rate limit, unless the `ITEM_TAGGING_*` settings say otherwise (see [Worker limits](#worker-limits)). It sits on a queue and in a process that Process Item jobs don't share, so a slow model call only delays other tagging jobs, never Processing, and a limit on the Item tagging queue never slows Processing. Out of the box nothing caps the calls to the model per minute. On Groq's free tier (about 30 requests and 8,000 tokens a minute, [Items ADR 0004](./contexts/items/adr/0004-ai-tagging-sends-an-item-excerpt-to-a-third-party-model.md)) a burst can get a `429`; the job's retries (30 s, then 60 s) absorb it, and an Item whose retries run out stays Ready without AI Tags. Those retries are unchanged by the settings, and a model `429` is not classified: it is an error like any other, and no `Retry-After` is read. To stay under that cap, set a rate limit (see the example under [Worker limits](#worker-limits)).
- **Consumer: the tagging worker (`apps/worker`).** `src/itemTagging.ts` is its entry point: it builds the tagging container (`di/taggingContainer.ts`: the database access, `TagItemUseCase` and the tag suggester, with no page fetcher), pings Redis and starts `createItemTaggingWorker` (`interface/itemTaggingWorker.ts`), a BullMQ `Worker` on `ITEM_TAGGING_QUEUE`. `tagItem` (`interface/processors/tagItem.processor.ts`) parses the payload (an invalid one is `UnrecoverableError`) and runs `TagItemUseCase`. It logs counts only (`suggested`, `applied`), never Tag names. A model error propagates, so BullMQ retries the job. On SIGINT/SIGTERM it finishes its current job, then closes Redis.
- **Tagging.** `TagItemUseCase` reads the Item's excerpt (`IItemRepository.findTaggable`: title, description, Source URL (the use case passes it through `sourceUrlForTagging`, which drops the query string, fragment and credentials), Item type, and the first `TAGGING_TEXT_LENGTH` (4,000) characters of its Text, cut in Postgres), the User's Tag names and the Item's Rejected tags (`ITagRepository`), and asks the `ITagSuggester` port. The pure rule `aiTagNames` (`domain/rules/aiTagNames.ts`) cleans the answer: each name through the worker's copy of `slugifyTagName`, invalid ones dropped, deduped, Rejected tags dropped, new names dropped once the User has 1,000 Tags, then the first 3. `DrizzleTagRepository.applyAsAi` puts them on (see [Tags → Concurrency](./tags.md#concurrency)). A deleted Item, before the model is asked or by the time the answer is written, is skipped quietly.
- **The model.** `OpenAiCompatibleTagSuggester` (`infrastructure/ai/`) calls an OpenAI-compatible chat API with the `openai` package: Groq by default (`openai/gpt-oss-20b` at `https://api.groq.com/openai/v1`), in JSON mode (`response_format: { type: "json_object" }`, which every Groq model supports), at temperature 0. The instructions are the system message; the Item goes in the user message as JSON, as content, never instructions. An answer that isn't `{"tags": [string…]}` throws, so the job is retried. The client's own retries are off (BullMQ's backoff owns them) and a call times out after 10 s (it holds the tagging worker's one job slot, so a hung model is cut off fast and the retries cover the rest).
- **Unconfigured.** Without `AI_TAGGING_API_KEY` ([Environment Variables](./environment-variables.md#appsworkerenv)), no suggester is bound: the tagging worker logs that at info on startup, and each Tag Item job completes without reading anything, logging at info.
- **Failure.** Its final-failure step, `tagItemFailed` (`interface/processors/tagItemFailed.processor.ts`), only logs a warning with the Item id: the Item stays Ready, without AI Tags. Every failed attempt is also logged by the tagging worker's `failed` handler (`onItemTaggingJobFailed`), as on the processing queue. The handler never marks an Item Failed.

## Running the workers

The two workers are two processes from one codebase (`apps/worker`), each with its own entry point (`src/itemProcessing.ts`, `src/itemTagging.ts`), bundled together by `tsup`. Each needs `DATABASE_URL` and `REDIS_URL`, which `dev` reads from `apps/worker/.env` and the built `start:*` scripts expect in the process environment (they load no file); the processing worker also reads the optional Supabase pair, the tagging worker the optional AI tagging trio (see [Environment Variables](./environment-variables.md#appsworkerenv)). Each also reads its own optional concurrency, rate limit and lock duration (see [Worker limits](#worker-limits)). Either can be started, restarted or stopped without touching the other: with the tagging worker down or misconfigured, Items still become Ready, and their Tag Item jobs wait on the Item tagging queue until it is back.

| Where              | Both workers                                         | One worker                                                                                                        |
| ------------------ | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Locally            | `pnpm dev` (every app) or `pnpm --filter worker dev` | `pnpm --filter worker dev:processing` / `pnpm --filter worker dev:tagging`                                        |
| Production (built) | two services, one per worker                         | `pnpm --filter worker build`, then `pnpm --filter worker start:processing` / `pnpm --filter worker start:tagging` |

`dev` runs both workers in one shell and stops both when it exits, which suits one machine and is for local use only. There is deliberately no combined `start`: a shell that runs both and waits would keep reporting healthy when one worker had crashed, and may not pass SIGTERM on to both, so neither would close cleanly. In production deploy `start:processing` and `start:tagging` as two separate services (each restarted, scaled or stopped on its own), so a supervisor sees each one's exit; the repo has no deploy configuration, so how is up to the operator. Each worker closes cleanly on SIGINT or SIGTERM, finishing its current job first.

### Connections to size before deploying

Each process opens its own connections, so splitting the worker raised the total. Compare these with your database's and Redis's connection limits before deploying:

| Process           | Postgres                                                 | Redis                                                                                                            |
| ----------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| API               | one pool, up to 10 connections                           | one shared connection (the Item processing queue's producer)                                                     |
| Processing worker | one pool, up to 10                                       | one shared connection (also the Item tagging queue's producer), plus the BullMQ Worker's own blocking connection |
| Tagging worker    | one pool, up to 10                                       | one shared connection, plus the BullMQ Worker's own blocking connection                                          |
| **Total**         | **up to 30**, three pools at postgres.js's default of 10 | **5**                                                                                                            |

Neither pool size is set in the repo, so postgres.js's default of 10 applies; the table counts each process once, so every extra replica adds its own pool and connections.

### Worker limits

Each worker reads three optional settings for its own queue at startup, from `ITEM_PROCESSING_*` or `ITEM_TAGGING_*` (names, units and validation are in [Environment variables](./environment-variables.md#appsworkerenv); the reasoning is in [Items ADR 0006](./contexts/items/adr/0006-worker-concurrency-rate-limit-and-lock-duration-are-configured-per-queue-from-the-environment.md)). Each worker logs the settings it runs with once at boot.

| Setting       | Default                    | Passed to the BullMQ `Worker` as                             |
| ------------- | -------------------------- | ------------------------------------------------------------ |
| Concurrency   | 1                          | `concurrency`: jobs run at once                              |
| Rate limit    | none                       | `limiter`: at most `max` jobs started per `duration` ms      |
| Lock duration | BullMQ's default of 30 000 | `lockDuration` (ms): how long a job may run before it stalls |

The defaults are today's behaviour, so deploying changes nothing until a variable is set. Tuning one worker never touches the other.

- **A rate limit is queue-wide.** BullMQ keeps it in Redis, so it applies across every worker consuming the queue: a second tagging worker shares the limit rather than doubling it. It limits how many jobs start per window, not model calls: a retry is a job start too.
- **Concurrency has no cap, but a process has one Postgres pool.** Each worker process opens one pool, 10 connections by default (the `postgres` library's default; nothing in Resonory sets it). Jobs beyond that wait for a connection, so raise the two together. The page fetcher and the Thumbnail pipeline have no concurrency limit of their own either: at concurrency N, up to N pages are fetched and N images resized at once, each holding its memory.
- **Lock duration and stalls.** A running job renews its lock on a timer. A job that can't renew in time (a long synchronous stretch starving the event loop, more likely with several jobs sharing one process, or a call that outlasts the lock) is treated as stalled and, past `maxStalledCount`, failed. A longer lock duration gives such a job room; a shorter one finds a dead worker's job sooner. With higher concurrency, lengthen it with it.
- **Example, not a default: Groq's free tier for tagging.** About 30 requests a minute is `ITEM_TAGGING_RATE_LIMIT_MAX=30` with `ITEM_TAGGING_RATE_LIMIT_WINDOW_MS=60000`. Nothing sets it for you: unset, Tagging has no limiter. On a paid plan, leave it unset or raise it, and raise `ITEM_TAGGING_CONCURRENCY`.
- **Retries are unchanged.** Process Item keeps 3 attempts from a 5 s backoff and Tag Item 3 attempts from 30 s. A model `429` that gets past the limiter is still absorbed by those retries, and a job that runs out of them leaves its Item Ready.

### Stuck Items

An Item can stay Processing with no job working on it: its job was lost (a flushed queue, Redis data lost), or the final-failure step threw. The processing worker ends such Items itself (`SweepStuckItemsUseCase`, `interface/processors/sweepStuckItems.processor.ts`):

- **A repeating job.** At boot the processing worker registers one repeating job, `sweep-stuck-items`, on the Item processing queue (`scheduleStuckItemSweep` in `infrastructure/queue/stuckItemSweepSchedule.ts`, a BullMQ job scheduler with a fixed id). BullMQ keeps one schedule and adds each run once, so a restart, or a second processing worker, shares it instead of multiplying it. The tagging worker has no sweep. A sweep job is never retried and finished ones are kept to the last 10; it counts as a job start for the queue's rate limit and takes a concurrency slot like any other.
- **What it does.** An Item that has been Processing for longer than `ITEM_PROCESSING_STUCK_AFTER_MS` (default 10 minutes, measured from when it was saved) ends the way a final failure does: Failed, and a Link when it has no Item type yet. The update only applies while the Item is still Processing, so a job that finishes in between wins and a sweep never overwrites Ready. A job that finishes after the sweep may still turn Failed into Ready. Ready and Failed Items, and Items younger than the threshold, are never touched. The sweep runs every `ITEM_PROCESSING_SWEEP_INTERVAL_MS` (default 5 minutes), so with the defaults a lost job's Item ends Failed 10 to 15 minutes after it was saved.
- **At most 500 Items a sweep, oldest first.** After a flush every lost Item is stuck at once, so one sweep ends at most 500 (`MAX_ITEMS_PER_SWEEP`) and the next sweep takes the rest, which keeps one run short. The query it reads is served by the partial index `items_processing_created_at_idx` (see [Database](./database.md#schema)).
- **Keep the threshold generous.** It has to outlast three attempts (backoff of 5 s and 10 s, plus each attempt's fetches) and the lock duration, or an Item whose job is still running or being retried would be failed early; a late finish would still make it Ready, but it would show Failed meanwhile. A backlog does the same: the sweep goes by when an Item was saved, not by whether its job has started, so a rate limit or a low concurrency that keeps jobs waiting longer than the threshold has the same effect. Raise `ITEM_PROCESSING_STUCK_AFTER_MS` with them. The same applies once a retry endpoint can re-queue an old Item, whose `created_at` is old; measuring from when Processing started would fix both (issue #198).
- **The sweep shares the processing queue.** Its job takes a concurrency slot and counts against `ITEM_PROCESSING_RATE_LIMIT_*` like any other job, so in a backlog the sweep waits behind the jobs ahead of it (the sweep is itself delayed by the same backlog that makes it fail Items early, which keeps it from failing many of them at once). A small queue and worker of its own would run it on time whatever the backlog; not built, as nothing needs it yet.
- **Logging.** Each sweep logs `swept the stuck Items` with how many it ended (`ended`), and a warning with the Item id and the error's name for each Item it couldn't end; the others go on. An error finding the Items (Postgres down) fails that sweep job, which is logged like any failed job, and the next scheduled sweep tries again.

### Before deploying: drain the old `items` queue

The single `items` queue is retired, with no compatibility consumer: nothing reads it any more. Before deploying the new API and workers, drain it (stop the old API, wait for the old worker to finish what is in it) or flush it, or its jobs are stranded. Do this together with the migrate-first step in [Database](./database.md#migration-workflow).

A flush loses the waiting `process-item` jobs, and an Item whose job was lost stays Processing until the stuck-Item sweep ends it as Failed (see [Stuck Items](#stuck-items); with the defaults, within about fifteen minutes of its save). To see which Items that will be, or to find them without waiting, use this query. A Process Item job gets three attempts over about a minute, so an Item still Processing after ten minutes has no job working on it:

```sql
SELECT id, user_id, source_url, created_at
FROM items
WHERE status = 'processing'
  AND created_at < now() - interval '10 minutes'
ORDER BY created_at;
```

There is no retry endpoint yet, so once the sweep has ended one, its User can save the link again.

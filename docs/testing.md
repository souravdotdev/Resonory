# Testing

[Vitest](https://vitest.dev) is wired into every app and package that has runtime logic worth testing, following the same "shared base + per-package config" pattern as ESLint and TypeScript.

## Shared config — `packages/vitest-config`

Two presets, mirroring the eslint-config split between plain Node packages and `apps/web`:

- `./node` (`node.mjs`) — plain Node test environment. Used by `packages/shared`, `packages/db`, `apps/api`, `apps/worker`.
- `./react` (`react.mjs`) — `jsdom` environment + `@vitejs/plugin-react`, built on top of `./node` via `mergeConfig`. Used by `packages/ui`, `apps/web`, `apps/waitlist`.

Every package with tests has its own small `vitest.config.ts` importing one of these, and a `test` script (`vitest run`). `apps/api`'s also merges in the `@/` alias (pointing at `src/`) that its `tsconfig.json` declares.

```bash
pnpm test               # vitest run in every package, via Turborepo; needs no database or Redis
pnpm test:integration   # the API's and the worker's Postgres-backed tests; needs Postgres (see below)
```

**Why the shared config files are `.mjs`, not `.ts`** (unlike every other shared config in this repo, which is `.ts`/`.js` extended via a package.json `exports` field): Vite's own config-file loader treats anything resolved through `node_modules` — which is how a pnpm workspace package resolves — as external and leaves it unbundled. A workspace package's raw `.ts` file can't be `import`ed directly by Node (no type-stripping applied), so a `vitest.config.ts` in one package importing a `.ts` file from `@resonory/vitest-config` fails with `ERR_UNKNOWN_FILE_EXTENSION`. Plain `.mjs` sidesteps this since Node can load it natively, no transform needed. Each _consuming_ package's own `vitest.config.ts` stays `.ts` — that file is the true entry point Vite bundles directly, so it doesn't hit the same issue.

**jsdom is pinned to `^29.1.1`, not the current `30.x`**: jsdom 30 requires Node `^22.22.2` or newer; this project targets Node `≥20`. jsdom 29 supports `^20.19.0`. If the project's Node baseline moves to 22+, this pin should move too.

## What's actually tested, and why

**`apps/api`** — the flagship test suite, and the direct payoff of the Clean Architecture layering (see [Clean Architecture](./clean-architecture.md)). Tests live in `apps/api/tests/unit/`, in folders that mirror `src/` (`domain/`, `application/`, `infrastructure/`, `interface/`). A use case receives its ports through its constructor, so a test builds it directly with hand-written fakes (`new AdmitSignInUseCase(fakeUserRepository)`, usually `vi.fn()`-based) instead of a container, a real database or Redis. A test that imports a decorated class imports `reflect-metadata` first. The few tests that need real Postgres live apart, in `apps/api/tests/integration/` (see [Integration tests](#integration-tests-apps-api)).

- `domain/rules/signInDecision.test.ts` — `decideSignIn`: an active User → allow, deleted 1 day ago → restore, deleted exactly 30 days ago → restore, deleted 31 days ago (or a moment past the Grace period) → refuse.
- `domain/rules/tagName.test.ts` — `slugifyTagName`'s normalization rules and 50-character limit, and that `TAG_NAME_PATTERN` (which the `tags` CHECK constraint embeds) accepts exactly the slugs it produces.
- `domain/schema-agreement.test.ts` — the Items tables in `@resonory/db/schema` agree with the Items domain: the `item_type`, `item_status`, `tag_source` and `tag_origin` enums hold exactly the domain's Item types, Item statuses, Tag sources and Tag origins (`TAG_ORIGINS`), and the Tag name check uses the domain's slug pattern and length limit. `packages/db` can't import the domain, so it keeps literal copies; this test is what stops them drifting.
- `application/use-cases/auth/AdmitSignInUseCase.test.ts` — with a hand-written fake `IUserRepository`: an allowed sign-in refreshes the Display name and avatar, a missing Google name keeps the current one, a restore also clears the deletion time, a refusal throws `UserPermanentlyDeletedError` and changes nothing, a missing Google photo clears the avatar, the email is never in the changes, and a missing User fails with `NotFoundError`.

## Integration tests (`apps/api`)

What a fake can't prove, because Postgres does the work (unique constraints, foreign keys, row locks under concurrency), is tested against a real database in `apps/api/tests/integration/`, mirroring `src/` like the unit tests. They run only through their own script, so `pnpm test` and the pre-push gate stay database-free:

```bash
docker compose up -d       # the Compose Postgres on localhost:5433
pnpm test:integration      # or: pnpm --filter api test:integration
```

`apps/api/vitest.config.ts` includes only `tests/unit/`; `vitest.integration.config.ts` includes only `tests/integration/` (with longer timeouts) and is what `test:integration` runs. The root `test:integration` is a Turborepo task, never cached, since its result depends on the database.

Each test file calls `createTestDatabase()` (`tests/integration/support/testDatabase.ts`) in `beforeAll`. It connects to the server in `TEST_DATABASE_URL`, by default the Compose Postgres (`postgres://postgres:postgres@localhost:5433/postgres`), creates a database with a unique name (`resonory_test_<random>`), runs every migration in `packages/db/migrations` with Drizzle's migrator, and returns a Drizzle handle over the real schema. `afterAll` calls its `drop()`, which closes the connections and runs `DROP DATABASE … WITH (FORCE)`; a failure while creating or migrating drops it too. The `resonory` database your dev servers use is never touched. Tests share their file's database, so each seeds its own Users (straight into the schema tables) and never sees another test's rows. `postgresErrorOf(query)` unwraps Drizzle's `DrizzleQueryError` to the Postgres error, for asserting a SQLSTATE and constraint name.

`infrastructure/repositories/DrizzleTagRepository.test.ts` calls the real `DrizzleTagRepository` (see [Tags](./tags.md#concurrency)):

- 8 concurrent `findOrCreate` calls for one new name → exactly 1 Tag, every call returning its id; a new Tag is created as the User's, and an existing Tag only the AI used becomes the User's;
- 20 concurrent creates for a User's last 10 Tag slots → exactly 10, the rest `UserTagLimitError`;
- creating a Tag → the User's Tags only the AI used that are on no Items (their Items deleted) deleted first, another User's kept, so one of them never counts towards the 1,000;
- `applyAsUser` on an `ai` link → `user`, its `created_at` kept; on a `user` link → unchanged; a Tag only the AI used becomes the User's;
- `applyAsUser` with another User's Tag → refused by `item_tags_tag_id_user_id_tags_fk`; with another User's Item, or an Item that no longer exists → `NotFoundError`; nothing linked in any of them (the missing Item is deleted before the call, so this covers the locked select's no-row branch, not a delete racing the lock; the race is reproduced in `TagItemUseCase.test.ts`);
- 10 concurrent links for an Item's last free slot → exactly 1, the rest `ItemTagLimitError`; a Tag already on a full Item is still re-applied;
- the composite foreign keys, at the SQL level the repository never reaches: an `item_tags` row joining one User's Item to another's Tag, or one User's Tag to another's Item, fails with `23503` on `item_tags_tag_id_user_id_tags_fk` / `item_tags_item_id_user_id_items_fk`;
- `removeFromItem` scoped to another User → nothing removed or recorded; scoped to the owner → only that link, the Tag and its other links kept;
- `removeFromItem` and Rejected tags → the Tag name recorded for the Item for an `ai` or a `user` link; nothing for a Tag that isn't on the Item; one row, the first, when the same name is rejected twice; the row kept after the Tag is deleted; the User still able to put the Tag back;
- `removeFromItem` on a Tag only the AI used → deleted with its last link, its Rejected tag kept; kept while it's on another Item; a Tag the User applied, or an AI Tag they confirmed with `applyAsUser`, kept on no Items; its last two links taken off at once → deleted; and the race #179 names, made deterministic: a stand-in for the worker's `applyAsAi` (the Item lock, then the User lock, then the link) holds its locks with the Tag linked to another Item while `removeFromItem` takes the last link off, and the Tag ends up kept, on that Item (without the User lock in `removeFromItem` it's deleted and the AI's link goes with it). The test waits, through `pg_stat_activity`, until the untag is blocked on a lock before letting the stand-in commit;
- `rejected_item_tags` at the SQL level → its rows removed when the Item is deleted; a row naming another User's Item refused with `23503` on `rejected_item_tags_item_id_user_id_items_fk`; a name that breaks the Tag name rule refused with `23514` on `rejected_item_tags_tag_name_is_slug`;
- `listForUser` → the latest link first, an AI link counting, a Tag on no Items by its own `created_at`, ties by name, only the User's Tags; a Tag only the AI used left out once it's on no Items (its Item deleted, before the User's next Tag deletes it);
- `findById` → the User's Tag, never another User's.

Removing either `for("no key update")` lock from the repository fails the two limit races, which is what these tests are for.

In CI they run as their own step after the main one, against a `postgres:16-alpine` service container (see [Code Quality](./code-quality.md#continuous-integration)).

- `applyAsAi` → new Tags created as only the AI's and linked with source `ai`; a Tag the User applied never made the AI's; an existing Tag reused by name, never another User's; a `user` link left untouched (source and `created_at`); run twice, nothing new; a rejected name neither put on nor created; at 19 Tags only the first name goes on, and a full Item gets nothing, creating no Tag; a User at 1,000 gets only existing Tags; the User's Tags only the AI used that are on no Items (their Items deleted) deleted first, another User's kept, so one of them never counts towards the 1,000, and a name the model gives again is made again as a new Tag; a deleted or another User's Item → null, nothing created; an empty list → nothing;
- under concurrency → 8 calls putting one new name on 8 Items end with one Tag on all 8; 20 creates for a User's last 10 slots let exactly 10 through, failing none; 10 calls for an Item's last free slot let exactly 1 through, creating only its Tag; and 10 AI calls racing 10 stand-ins for the API's `applyAsUser` (the same Item lock and count, no User lock) never push the Item past 20; and, the other side of #179's race, a stand-in for the API's `removeFromItem` (the Item lock, then the User lock) holds its locks after deleting a Tag only the AI used with its last link, so `applyAsAi` putting that name on another Item waits, then makes the Tag again (only the AI's) and puts it on, never linking the deleted one.

Removing the User-row lock fails the User-limit race, and removing the Item-row lock fails the race against `applyAsUser`'s stand-in, which is what those tests are for.

`infrastructure/repositories/DrizzleItemRepository.test.ts` checks `findTaggable`: the Item's title, description, Source URL, Item type and Text; only the first 4,000 characters of a long Text (cut in characters, not bytes); nulls for an Item without them; nothing for another User's Item or a missing one. It also checks the sweep's two queries: `findProcessingBefore` finds every User's Items still Processing that were saved before the cutoff, oldest first and at most `limit` of them, never a recent, Ready or Failed one; `markFailedIfProcessing` turns a Processing Item Failed with the given Item type, leaves a Ready or Failed Item exactly as it was and answers false, and never touches another User's Item or a missing one; and the migration creates the partial index `items_processing_created_at_idx` (`created_at`, `WHERE status = 'processing'`).

CI runs them in the same step as the API's (the root `test:integration` runs both).

## Fakes over mocking libraries

Every fake used across these tests is either a small hand-written object literal or a `vi.fn()` — no separate mocking framework, and no shared "fakes" package. Given how small each port interface is (1-3 methods), writing the fake inline in the test file that needs it is less overhead than maintaining a shared fixture module, and keeps each test file readable on its own.

The one exception: when a single fake serves both the use-case tests and the route tests (`app.test.ts`) of a slice, it's written once in `apps/api/tests/unit/fakes/` and imported by both, rather than copied, so the two seams test against the same behaviour. Today that's `fakes/tagging.ts` (`taggingInMemory()`), the in-memory Items, Tags, Tag links and Rejected tags behind `TagItemUseCase`, `UntagItemUseCase`, `ListTagsUseCase` and the Tag routes. A fake used by only one test file stays inline in it.

## Pre-push gate

`.husky/pre-push` runs `pnpm lint && pnpm check-types && pnpm test` — tests are part of the last gate before code leaves the machine, alongside lint and type-checking (see [Code Quality](./code-quality.md)). They're not part of `pre-commit` (`lint-staged`), since running a full test suite on every commit — including ones that don't touch tested code — would slow down the fast, scoped pre-commit check down considerably. The integration tests aren't in the gate either, since it would then need Postgres running; CI runs them.

## A real bug this setup caught while being built

Building the `apps/api` route tests originally surfaced a genuine regression risk: `tsc` (then `apps/api`'s/`apps/worker`'s build tool) compiled `*.test.ts` files into `dist/` alongside real source, and Vitest's default file-discovery glob picked up both the source test and its compiled `dist/` copy — silently double-running every test, and shipping test files in what's meant to be production build output. Originally fixed by excluding `**/*.test.ts`/`**/*.test.tsx` in those apps' `tsconfig.json`. That exclusion was later removed once `apps/api`/`apps/worker` switched their production build to `tsup` (see [Architecture](./architecture.md#monorepo-layout)) — a bundler only pulls in files actually reachable from its entry point, so test files never leak into `dist/` regardless of tsconfig excludes, and removing the exclusion restored `tsc --noEmit`'s type-checking coverage for test files, which it had been silently skipping. The `**/dist/**` exclude in the shared Vitest config stays in place regardless, as a second line of defense.

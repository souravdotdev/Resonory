# Logging

Every app logs through [Pino](https://getpino.io), configured once in `packages/logger` rather than independently per app. The reasoning: before this, `apps/api` got Pino only as Fastify's untouched default, `apps/worker` and `apps/waitlist` had about fifteen scattered `console.*` calls between them, and `apps/web` had none — no shared format, no verbosity control, no redaction, and the project's one real logging discipline (never log a raw error's message, since a database driver's message can carry SQL and a visitor's email address) existed only as one app-specific helper. See [ADR 0006](./adr/0006-a-shared-logger-package-with-correlation-by-argument.md) for the shape this took.

## Current state: one shared factory, every app's own correlation convention

`packages/logger/src/base.ts` exports `createLogger({ name, bindings? }, destination?)`. Every app's composition root calls it exactly once, building a process-lifetime (or, where there's a container, DI-bound singleton) logger — nothing else in the project constructs a Pino instance directly. `destination` is a test-only escape hatch (an injectable stream), never passed in real app code.

- **Format.** `base: { app: name, ...bindings }` tags every line with which app produced it. `timestamp: pino.stdTimeFunctions.isoTime` gives human-correlatable timestamps. In development (`NODE_ENV === "development"`), a `pino-pretty` transport (colorized, human timestamps) runs; in production and test, Pino writes raw NDJSON straight to stdout, no transport at all — the fast path, and what a deploy's own log capture expects.
- **Level.** `LOG_LEVEL` (one of Pino's levels), else `info` in production and `debug` everywhere else. See [Environment Variables](./environment-variables.md) for `packages/logger/src/env.ts`'s validation — an invalid `LOG_LEVEL` fails loudly at import time, the same convention every other `env.ts` in this project follows.
- **Redaction** (`packages/logger/src/redact.ts`). A single mechanism: `redactSensitiveFields`, a recursive walk applied via Pino's `formatters.log` hook, masks any field named (case/separator-insensitive) `email`, `token`, `apiKey`/`api_key`, `password`, `secret`, or a service-role-style key, at any nesting depth — not just the top level, and not just a fixed set of known paths. The walk is scoped to genuine plain objects (`isPlainObject`): it does not recurse into `Error`, `Date`, or anything else that exposes its data through prototype getters rather than its own enumerable properties, since Fastify's `Request`/`Reply` are exactly that shape (`method`/`url`/`statusCode` are getters) — recursing into those would silently flatten them to `{}` and break Fastify's own request-completion logging. This is a safety net, not the primary defense: it exists on top of call-site discipline (below), never instead of it.
- **`describeError`** (`packages/logger/src/describe-error.ts`, moved here from `apps/waitlist`). Surfaces only an error's `name` and, when present, its `code` — never its `message` or `stack`. A database driver's message can carry a SQL query and its parameters (a visitor's email address, for instance), so no call site anywhere in the project passes a raw `Error` into a log call; every error log site calls `describeError(error)` first and logs that string. `apps/waitlist` additionally has `logSafeError(logger, error, message)` (`apps/waitlist/src/logger.ts`), a small wrapper around `logger.error({ err: describeError(error) }, message)`, so this shape is written once rather than repeated at every call site.

## Correlation: one id bound per unit of work, by argument, not by injection

Each app ties related log lines together differently, matching its own existing architecture rather than forcing one pattern everywhere:

- **`apps/api`.** The logger is bound as `TOKENS.Logger`, a `createLogger({ name: "api" })` singleton, the same way `TOKENS.Database` is bound. Fastify is built with `loggerInstance: container.get(TOKENS.Logger)` (not the `logger: true`/`logger: {...}` boolean-or-options form) — Fastify still mints its own per-request `reqId` and logs the request-completion line (method, url, status, response time) for free, now through the shared instance. **Convention, not yet used:** a future piece of business logic that wants to log receives the request-scoped logger (`request.log`) as a plain argument from its caller — the same way `request`/`reply` already flow into a controller — rather than as a constructor-injected port, since a port is one adapter for the process's life, but the binding (`reqId`) changes per call. See the comment on `ItemsController`.
- **`apps/worker`.** The logger is bound as `WORKER_TOKENS.Logger`. Once a job's payload parses, `processItem.processor.ts`/`processItemFailed.processor.ts` derive `logger.child({ itemId })`, so every log line produced while handling that job carries the Item's id without repeating it at each call site; `itemsJobFailed.ts` likewise binds `.child({ jobId, jobName })`. **Mechanism documented, not yet wired:** nothing inside `ProcessItemUseCase` logs internally yet, so there's no job-scoped logger reaching it — the comment next to `WORKER_TOKENS.Logger`'s binding in `container.ts` describes the short-lived Inversify child-container approach (`container.createChild()`, rebinding just the logger token) for whenever that changes.
- **`apps/waitlist`.** No per-request id. `apps/waitlist/src/logger.ts` exports one plain singleton (no DI container here — [ADR 0005](./adr/0005-the-waitlist-app-is-feature-first-without-a-di-container.md)); it's a single low-traffic endpoint with one code path, so the complexity of threading a request id through it wasn't judged worth it.
- **`apps/web`.** `apps/web/src/server/logger.ts` exports a logger, ready for whenever server-side logic here needs one — nothing logs yet. It's guarded with `import "server-only"` (the real npm package, not just a comment), so an accidental import from a `"use client"` file fails the build rather than silently doing nothing.

## Testing

Every test that exercises a log call site asserts on the logger's actual structured output, not on mocked `console` calls (that convention predates this package and still holds — see [Testing](./testing.md)):

- `packages/logger`'s own tests write to an in-memory destination stream (via `createLogger`'s test-only `destination` parameter) and parse the NDJSON lines, rather than mocking Pino.
- `apps/worker` has a small recording-logger test fake (`tests/unit/testLogger.ts`): a plain object satisfying `.info`/`.warn`/`.error`/`.child`, recording `{ level, bindings, msg }` per call, with `.child()` returning another recording logger that merges bindings. Every worker test that previously spied on `console.*` now asserts against this instead — strictly more precise, since it checks exact fields rather than substrings of a printed line.
- `apps/waitlist` spies on the shared `logger` singleton directly (`vi.spyOn(logger, "error"/"info")`) in place of the old `console` spies; the existing "never logs the visitor's email address" assertions carry over against the structured field.
- `apps/api` has one test confirming `buildApp` is called with `loggerInstance`, and a separate end-to-end test (`tests/unit/logging.test.ts`) that builds a real app with an injectable-destination logger, makes a real request via Fastify's `.inject()`, and asserts the request-completion log line actually carries a `reqId`, `method`, `url`, and `statusCode` — not just that the wiring exists.
